# brownie — sealed session state, full stack

The brownie is cold3's client-carried sealed session state, managed automatically on every POST by fetchWorker on the page and doorWorker on the server. The system stands full stack and runs empty: no note lives in a brownie yet, and TOTP still uses its own envelope cookie, unchanged. This document tells the design as it exists, and the steps ahead.

## [1] sessions: the twenty years we're standing on

The brownie looks bespoke, so this section places it in the tradition it actually belongs to — what a session object was, how its implementations evolved, what serverless killed, and what the current by-the-book answer is for exactly our stack. Short version: cold3 runs a session split in two, and both halves are classic patterns; the brownie's bespoke parts are a few reasoned deviations, not a new invention.

**The traditional session object.** In the LAMP era, PHP's `session_start()` did three things invisibly: minted a random session ID, set it in a cookie (`PHPSESSID`), and handed your code `$_SESSION` — a magic array that persisted between requests. The mechanism underneath was mundane: the server serialized that array to a file on its own disk (`/var/lib/php/sessions`, one file per session) and reloaded it on every request by cookie ID. Every mainstream framework shipped the same shape under a different name — Java servlets' `HttpSession`, ASP.NET's `Session`, Express's `MemoryStore`, Django's sessions (database-backed by default, which mattered later). The assumption baked into all of them: one server, with persistent memory and disk, seeing every request from every user.

**Scaling broke it before serverless did.** The moment you ran two app servers behind a load balancer, a user's second request could land on the box that didn't hold their session file. The first patch was sticky sessions — the balancer pins each user to one server by cookie or IP — which is fragile in exactly the ways you'd guess: a deploy or crash on that one box logs out everyone pinned to it, and autoscaling fights the pinning. The durable fix was externalizing the store: sessions moved to memcached and then Redis, and "session ID in a cookie, session data in Redis" became *the* standard architecture of the 2010s. The `$_SESSION` abstraction survived unchanged; only its backing store moved out of process memory onto the network.

**Why Redis and memcached, and not just the database behind the farm?** memcached was born at LiveJournal in 2003 as a read cache for database queries generally — the database was the bottleneck and RAM on spare boxes was cheap — and sessions moved in because they are the hottest, tiniest records a site has: every page view reads one and most write one back, multiplied by the entire concurrently-active userbase, a flood of trivial queries hammering the same database that serves the real ones. The full list of reasons it wasn't "just the database": latency (spinning-disk era — a database round trip cost milliseconds to tens, memcached answered sub-millisecond from RAM), access pattern (pure key-value, no SQL needed), expiry (sessions die on their own; caches evict by TTL natively, where SQL needs cron sweeps of dead rows), and durability economics (losing sessions logs everyone out — annoying, not catastrophic — so paying the database's fsync-and-WAL guarantees for them is waste). Redis, from 2009, won the category by adding optional persistence and richer data structures. The sizing intuition that goes with this: database-backed sessions are fine for small sites — Django shipped that as its default — and the external store earns its keep at the scale of a big farm with thousands of simultaneously active users. Note the resonance with our design: the brownie keeps ephemeral twenty-minute state out of Supabase for exactly the reasons sessions left the database at scale — hot, tiny, expiring, and undeserving of durability.

**The second lineage: the client carries the state.** All along there was an alternative — put the session data itself in the cookie, signed or encrypted so the client can carry it but not read or forge it. Rails made this its default (CookieStore, since Rails 3); Flask sessions are signed cookies; the JWT wave applied the same idea to auth tokens; the `iron` sealing library formalized encrypt-and-MAC blobs as a reusable primitive. The server holds nothing, which scales to any number of servers for free. The costs are structural: the ~4KB cookie ceiling, revocation is hard (the server can't delete a token it doesn't hold — the JWT world's chronic wound), and replay needs deliberate defense. This is the lineage our sealed envelopes have always belonged to.

**What serverless changed.** Workers and lambdas deleted lineage zero — there is no process memory or local disk that survives from one request to the next, and no sticky balancer can change that. The two survivors are exactly the two lineages above: an external store keyed by an ID cookie (on Cloudflare: KV, Durable Objects, D1, or your own database), or client-carried sealed state. Nothing new was invented for serverless; the field just narrowed to the two designs that never depended on server memory.

**The by-the-book answer for Nuxt on Cloudflare.** Telling, for us: h3 — the HTTP server Nitro runs, the one our doorWorker already wraps — ships `useSession`, which is encrypted, password-sealed cookie sessions, and the blessed community module `nuxt-auth-utils` is a thin wrapper around that same sealed-cookie mechanism. The framework-endorsed, current mainstream pattern *is* our envelope, with a cookie as the parking spot. The alternative by-the-book path is a session store on KV or Durable Objects — external state we've deliberately declined, keeping Supabase as our one store.

**Where cold3 stands in this history.** We run a session split in two, each half a classic. Identity is `browserTag` + `credential_table`: an ID cookie whose backing store is the database — lineage one, the Django-and-Redis shape, with Supabase as the store. The brownie is lineage two — sealed client-carried state — reserved for exactly the data that shouldn't burden the database: provisional, twenty-minute, in-flight flow state. Traditional `$_SESSION` mashed both kinds of state into one server-memory bag; serverless forced the split, and the split is better, because each kind of state lands in its natural home. The brownie's bespoke parts are deviations from the sealed-cookie default, each reasoned: localStorage instead of cookie transport (the ciphertext rode every request for nothing, and 4KB caps growth), explicit body carriage (the server reads it from where we deliberately put it, never as ambient header state), and one shared letter whose notes each name their own owner — a shape neither lineage has, and the piece that serves housemates and sign-ups alike. The name is bespoke; the pattern is twenty years old and currently canonical.

## [2] the brownie in one view

One localStorage entry per browser, under the hardcoded key `brownie`, holding a single sealed envelope — the bare base62 ciphertext, completely opaque to the page, which can neither read nor forge it. The letter sealed inside carries `browserHash` and `notes`, plus the `action: 'Brownie.'` and `expiration` that sealEnvelope stamps. Each note is a self-describing object naming its own `type` (like `'Totp.'`), its own `expiration` (a positive integer epoch — every note must have one), and its own owner:

```
letter:  {browserHash, notes: [{type: 'Totp.', expiration: 1784764575418, userTag: 'Wx8FRH7WvMpsdqZw7gjAH', ...}, ...]}
```

Ownership lives per note, and that one choice carries several stories at once. Housemates sharing a browser profile share the one brownie, their notes mixed in the same array — Alice finishing her totp flow reseals a letter still carrying the note Bob needs when he sits down next — and request code touches only notes whose `userTag` matches the signed-in user it resolved from the database. A note can also be owned by nobody yet, which is how a sign-up flow can hold provisional state before its person has a userTag, matching the current pattern where otp during sign-up completes before any tag exists. And privacy between housemates is total, since userTags appear only inside the ciphertext — nothing in devtools reveals who is mid-flow, or that anyone is.

The brownie is entirely ephemeral — notes are labeled to last twenty minutes, some perhaps an hour — and maintained by replace-always: the server answers with a complete replacement or a delete, never an edit, and only when the server needs the page to keep something does a brownie exist at all. Most users most of the time — nearly all of the time — hold none, because a brownie exists only during the minutes of an in-flight flow.

## [3] the wire protocol

`body.brownie` rides in the serialized JSON of the POST body and the response body.

**Up, page to server** — a presentation, not a command. The page sends the base62 ciphertext it holds, alone:

```
body.brownie           the bare base62 ciphertext, the value straight from localStorage
```

**Down, server to page** — an explicit command, or silence:

```
body.brownie.action    'BrownieSet.' or 'BrownieDelete.'
body.brownie.envelope  with BrownieSet.: the resealed ciphertext to store
```

`BrownieSet.` means: store this envelope, replacing whatever you held. `BrownieDelete.` arrives bare and means: you hold nothing in flight; clear the entry. And an absent `body.brownie` in a response is not a command at all — that response answered a request from before the current brownie state and has no standing to change it. This third outcome is load-bearing: the spa fires overlapping POSTs in tight clusters, most having nothing to do with the brownie, and a response to a request that departed brownie-less must stay silent, or a telemetry response landing late would wipe an enrollment brownie stored moments before. Silence answers the mirror case too: a request that carried the brownie up but didn't change it gets no command back, because a stale replacement from its late-landing response would clobber whatever the page stored after it departed. Delete is therefore always an explicit command, never inferred from silence.

## [4] the page side

fetchWorker handles the brownie before and after every POST, automatically — no store, component, or page code participates, and none could, since the contents are opaque. Before sending: append the held ciphertext as `body.brownie`. After receiving: if the response carries `body.brownie`, execute its action; otherwise touch nothing. Underneath sit two private level2 functions barely bigger than their names — `brownieGet` is `localStorage.getItem('brownie')` behind the platform guard, and `brownieApply` is `setItem` or `removeItem` by command — and that's the entire page side: no state, no keys to compose or parse, no expiration logic, no cleanup pass, nothing wired into the spa's lifecycle. The page cannot judge a brownie's freshness and never tries; an expired one rides up once, and the server's delete command comes back.

## [5] the server side

doorWorker handles the brownie around every handler through two helpers that pair with the envelope functions they wrap, both mutations visible at the door's own call sites: `door.brownie = await openBrownie(...)` on the way in, and `sealBrownie(...)`'s command onto the response on the way out.

**Opening, and the security tabletops.** `openBrownie` decrypts the arriving envelope — decryption itself proving the letter is authentic, stayed secret, and wasn't tampered with — then runs the sanity checks, and here the design commits to a rule: **the door never tosses over a brownie.** The cookie and localStorage can fall into a combined state that a toss would turn into a blown-up error page on every visit, forever — an infinite loop ending in a support call and someone clearing localStorage by hand. Instead, every failure degrades to an empty letter, which the response turns into `BrownieDelete.`, cleaning the browser up in one request. The tabletops: someone in devtools deletes the entry and retypes it as the literal word "brownie" — not even valid base62, decryption throws (as crypto helpers should on bad ciphertext, and this is a legitimate try/catch at the bottom gate, converting exception-speaking crypto into values) — delete. Our own letter shape changes at a deploy — every browser's stale brownie fails to open and gets cleared by its next POST — delete. Alice clears her cookies, so the site issues her browser a new browserTag, but localStorage still holds the old brownie — the sealed `browserHash` disagrees with the one her request's cookie proves, mild chaos and common — wipe the notes, delete. A malicious extension feeds Alice a brownie exfiltrated from an attacker's own signed-in browser, hoping she completes a flow bound to his account — same browserHash mismatch, and the request's cookie is what we trust — wipe, delete. A note missing its positive integer expiration — dropped. Expired notes — dropped one at a time, and a letter that empties commands its own deletion.

**Sealing.** After the handler returns, `sealBrownie` speaks only when it must: notes changed by this request — stamp the browserHash fresh from the request's cookie, seal with a duration reaching the latest note's expiration, command `BrownieSet.`; notes gone — command `BrownieDelete.`, because the server never seals an empty letter; notes carried but untouched — silence, judged by comparing the notes against the snapshot the door took at open; no letter at all — silence.

**The request-code contract.** `door.brownie` is the decrypted, mutable letter, reachable by every function in the request's call stack — read it and change it in place, and the door seals whatever it holds on the way out. Scope everything by owner: touch only notes whose `userTag` matches the signed-in user you resolved (or whatever an unowned sign-up note matches by, which is that flow's design); other users' notes ride along untouched. Starting a flow where no brownie arrived: `door.brownie = {notes: []}` and push your note, owner included.

## [6] carried and applied every time, like the cookie it replaces

A cookie rides every request automatically — unnecessarily, but conveniently. The brownie does the same, deliberately, because we control both sides of the doorway: fetchWorker appends the held brownie to every POST, and doorWorker examines every arriving body. Most requests have nothing to do with the brownie, and that costs almost nothing — a page holding no brownie appends nothing, and a request carrying one gets it validated in microseconds and resealed only when the request changed it. What makes always-carriage safe where a cookie's is sloppy: the carriage is explicit body content the server reads on purpose, the response side is explicit commands rather than inference, and the whole exchange is invisible above the fetchWorker/doorWorker seam.

Always-carriage plus overlapping POSTs is also where the design accepts its one race. Responses land in whatever order the network returns them, and reseal-on-every-carry would have made every response a writer: a telemetry response landing late would re-assert the letter as it stood at departure, resurrecting a note a faster response had just deleted. Silence-on-unchanged removes that whole class — only a request that changed the letter speaks — leaving the narrower case of two mutating requests in flight at once, from two tabs, where the last response to land wins and the other's change is lost or undone. We accept that deliberately, the way sealed-cookie sessions always have: it takes two same-user tabs changing flows inside one round-trip window, a lost note costs at worst a restarted twenty-minute flow, and a resurrected note is provisional state that every flow re-validates against the database at the moment it matters.

## [7] the steps ahead: totp, then the fork

**Totp moves in.** The first note. The endpoint branches for `TotpEnroll1./Enroll2.` read and mutate `door.brownie` directly — no per-endpoint open or attach, since the door does both — with level3's totp trio taking the letter and working its notes, the same shape as `credentialOtpSend/Enter`, scoped by owner: find the `'Totp.'` note whose `userTag` is the resolved user's. (Commit Jagu38 holds a working version of the letter shape from an earlier pass — the level3 functions, their grid tests, and TotpPanel's watch and cancel — reusable with the array renamed to notes and per-note owners added.) TotpPanel drops `useTotpCookie` and watches the store's `enrollment` ref; a cancel action removes the note server-side; recovery becomes a client-only follow-up `Get.` after mount, whose brownie rides automatically — the accepted cost is a brief flash on the rare mid-enrollment refresh, and the follow-up must send `envelopeOtp` along so an empty answer doesn't clear live otp challenges.

**Then otp, and the fork.** OTP's challenge envelope still lives in the `temporary_envelope_otp` cookie, and its future is the open fork: relocate into the brownie as notes beside totp's, or eliminate into credential_table event-3 rows, decided case by case. The cookie itself retires under either arm: a sealed blob the server never reads from a header rides every same-origin request doing no useful work, and the ~dozen simultaneous challenges that fill the browser's 4KB cookie ceiling are a limit counted nowhere. OTP is the strongest candidate for rows — server-generated, short-lived, already half-recorded in the table — leaving eliminate's marginal cost at storing the answer in the row plus expiration-by-row_tick and cancellation rules. For relocate: sealing is stateless, codes stay encrypted at rest, expiration stays enforced in one sealed place — and per-note owners plus ownerless notes fit signup-era otp naturally. The brownie exists either way; the fork decides tenancy, not construction.

## [8] open questions

**Should a discarded brownie be logged?** Failures at open now self-clean via `BrownieDelete.`, but a browserHash mismatch or undecryptable envelope is also a signal — the extension tabletop above is an attack. If we ever want eyes on it, `openBrownie`'s failure paths are the spot for a `logAudit`.

**When does the userTag get minted for a pre-authentication person?** Softer than it was: ownerless notes mean the brownie no longer forces the answer — a sign-up flow can hold provisional state with no tag at all. Whether early tags are still wanted for other reasons (pre-user favorites and follows, the credential.md design) stays deferred with the signup-phase work.

**Cross-tab reactivity.** Tabs share the entry and read fresh at each use, which is safe — a stale post is the replay case the flows already defend. The `storage` event could push updates between tabs; add a listener when a real flow benefits.

**The sudo note.** Shapes itself when it arrives — a type, an expiration, an owner, whatever the elevated action needs. The notes array means waiting costs nothing.
