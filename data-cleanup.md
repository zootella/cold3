# data cleanup

address_table and service_table are gone — out of the code, out of the schema, and out of the planning documents. Both were superseded by tables we since built and use: address_table's job is credential_table's, and service_table's job is split between ledger_table, trail_table, and credential_table. The removal itself was small, and this document is not a record of it. It is the design those two tables held, rescued before their scaffolding was deleted, and the list of what that design asked for that nothing does yet.

**This document illuminates; it does not resolve.** Every open question below is written down so it can be answered later, in its own turn, with the attention it deserves. Nothing here should be read as a decision, and the value of the document is that it makes the full set of loose ends visible at once, so a later pass can resolve them and shrink this file rather than discover them one at a time. As each open item is built or waived, it leaves — and when the last one does, so does the document.

## Why we can't just excise them

Because the scaffolding is the only place some of the design is written down. These two tables were specified early and carefully, and the comments, essays, and notes files around them record what we wanted to be able to accomplish — the questions we meant to be able to ask of the data, the flows we meant to support, the way a staff member or a support conversation would use what we'd kept. The tables were never built out, so none of that intent lives in working code. It lives in the notes.

The successors can carry every one of those jobs. The catch is that "can" is not "does." credential_table records the challenge lifecycle, trail_table records the rate-limit facts, and ledger_table records the third-party call — but only along the paths where somebody wrote the call. Delete the note that says "record which provider we used and how it went" before checking that a ledger row actually lands on that path, and the requirement quietly evaporates along with the table that was going to hold it.

So the order is: capture the design here, check each thing it wanted against what the three live tables actually record today, list whatever isn't done, and only then delete. Each unfinished item gets built into the successor table or gets officially waived — the point is that the choice is made deliberately rather than by omission.

The worked example the whole cleanup is about: a user asks to prove alice1980@gmail.com, we pick a provider like Twilio., we send a code, and the person enters it or doesn't. Chronicling that completely — for the user's own history, for a support conversation, and for judging how the provider behaved — is exactly what these two tables were for, from two different angles.

## address_table: the design, as the notes have it

**The shape.** Nine columns: the three margins, then `user_tag`, `type_text`, the address triad as `address0_text`, `address1_text`, `address2_text`, and `event`. Two indexes: `address1` on `(hide, user_tag, row_tick DESC)` to filter by user, and `address2` on `(hide, type_text, address0_text, row_tick DESC)` to filter by address.

**The idea.** An address is anything that names a person on some channel — an email address, a phone number for SMS, and explicitly also things like an Ethereum wallet address. All of them get one table, three normalized forms each: form 0 normalized for matching as unique, form 1 formal for handing to an API, form 2 for showing the user. The table is a ledger of events rather than a state row, with the vocabulary `2 mentioned, 3 challenged, 4 validated, 1 removed`.

**The two questions it existed to answer,** stated in a comment above the pair of functions meant to answer them. First, *given an address, get the user who we've challenged it for, or validated, and has not removed it* — returning a user tag and an ownership level of 3 or 4, or falsey if the address is available. Second, *given a user, get the addresses we've challenged and validated, that have not been removed* — an array of addresses, of different types, with events collapsed to the most recent 3 or 4. The comment works through the collapse rule out loud: if there's a 1, knock that out and all earlier records, then look for a 4, then a 3.

**The user story underneath it,** from the notes file. A new person navigates to the site, enters an address, and is assigned a user tag; the server sends a code and the person ignores it. The next day they return in the same browser and are still signed in, and still ignore the prompt. On the third day they open a different device and enter the same address — and now finding the code is required, and entering it both validates the address and signs them in on the new device without minting a duplicate account. The notes are explicit that this flow needs no provisional user level: the first browser to challenge a never-before-seen address simply gets a new user tag, signed into that browser without expiration, with the address recorded as challenged. A related note adds the case where a person who is not signed in follows a creator, and the follow has to survive a week — a user tag minted at the first piece of information, with the rule that the only way to make it durable is to complete signup on that browser, and no merging if they instead sign in as somebody else. Both of these are signup-era flows rather than table design, and they already have a home in the first-night-accounts material; noting them here only so the deletion pass doesn't look like it dropped them.

**Where it lives now.** credential_table took the design nearly unchanged and widened it. The triad is `f0_text`, `f1_text`, `f2_text` with the same three meanings. `type_text` widened from address types to every credential type. The `event` column kept the exact vocabulary. The two indexes have direct descendants: `credential1` filters by user, and `credential2` through `credential4` filter by type and each form. `credentialOtpHolder` is `addressToUser`, and `credentialOtpGet` is `userToAddress` — including the collapse rule, implemented as highest visible event wins, and documented in the essay above the otp credential functions.

## What address_table planned that credential_table hasn't taken up

Four items. Each one either gets built into credential_table or gets waived on the record.

**Event-1 removed rows are never written.** This is the largest of the four and it belongs to a bigger question, so it has its own section below.

**There is no all-types view of what a user controls.** `credentialOtpGet` answers the `userToAddress` question one type at a time — pass `Email.` and get that user's email addresses with their events collapsed. The design asked for the array across types in one call, which is what `credentialGet` would be, and `credentialGet` is an exported function with a ttd where its body should be. Nothing needs the combined view today because the credential panel asks per type, but a profile page or a support tool would want it, and the empty stub is currently the only trace of the requirement.

**There is no cross-type holder lookup.** `credentialOtpHolder` takes a type, and wallets have their own `credentialWalletHolder`. Asking "does anyone control this string, whatever kind of address it is" has no single call. Nothing needs it today; the question is whether it should exist before the type list grows.

**The ownership-level return was deliberately narrowed, and that decision is worth recording as made rather than pending.** address_table's `addressToUser` was to return a user tag *and* whether ownership stood at 3 or 4, treating a live challenge as a form of claim. `credentialOtpHolder` returns only event-4 holders and answers falsey for a challenge, with the reason stated at the line: mentions and challenges don't reserve an address for anyone. The grid suite proves the resulting behavior in both directions — an unproven mention reserves nothing, and a completed proof claims exclusively — so this is a change we made on purpose and should stop describing as a gap.

One more cluster sits in the same comment region and will be deleted by the same pass, though none of it is address_table's: the scraps left from the long-deleted browser_table. Four things were in them, and none has a home anywhere else, so each needs one or an explicit goodbye.

The `domain_text` idea: local storage is scoped to protocol, port, subdomain, and domain, so a browser tag from localhost is already a different tag from one at the live domain. Recording which host a browser tag came from would let one database sit behind the same code on several domains and still show a user — or staff — which browsers on which domains an account is signed in from. The note believes sign-in across domains already works without it, and that what's missing is only the panel that displays it.

The `level` column, which was 1 provisional, 2 normal, or 3 for starting an hour of elevated permission on one device for a destructive operation. The elevated hour appears in the notes files as a security idea in its own right, and this was the column that would have carried it.

**Sign-out was recorded, and no longer is.** The scraps name a `queryAddRow` that wrote where and when a user signed out, from which browser — a fact that simply stopped being kept when browser_table went. Today `credentialBrowserRemove` hides the rows and leaves nothing behind. Under the direction data-plan.md sets this is a ledger row rather than a column, which makes it less a loss to mourn than a call site to write when the credential flows get their audit pass.

`client_table`, named once as the successor that would take browser_table's place: standard margins, keeping hashes of the clients that make and hide rows. Nothing was ever built, and the name appears nowhere else in the repository. Of the four this is the easiest goodbye, because what it was reaching for is nearly in hand already. It wanted a durable way to say *this client, here, doing this* — the thing staff need when they have to reconstruct how somebody was taken advantage of, or how an attacker got where they got. There is no client identifier in this system and there is not going to be one; what stands in its place is browser hash and user tag, recorded in ledger_table beside each mutation and in hit_table beside each visit's connection details, so the two join on the same identifiers and the sequence assembles. The capability survives its table.

## Three competing patterns for making a row go away

The event-1 question is a small instance of an unsettled rule that runs through the whole schema. Three patterns compete, all of them present somewhere in current code, early code, or the planning notes, and no rule says which applies where. Sizing this is the point of the section; standardizing is a significant effort for a later sprint.

**Pattern one: delete the row.** We don't do this, and the house style says so outright — the design notes open with "tables are ledgers; we append to them" and "instead of deleting a row, mark it as hidden." The query surface backs that up by omission: level2 exposes no delete verb at all, so application code has no way to remove a row even if it wanted to. The only DELETE statements anywhere are the grid harness's `clear()` for emptying a table between tests and an unreachable `_delete()` branch in the supafake adapter. But deletion is not absent from the *design*. trail_table carries an `expiration` column defined as the tick at which a row could be removed from the database, with 0 meaning never — and its own comment concedes that no system presently clears expired rows. The `trail1` index comment names both verbs, "hide or delete old rows quickly." In production nothing passes an expiration, so every trail row we write says keep forever; only a grid test exercises the parameter. So this pattern is specified in one table's schema, has no implementation, and would need a level2 verb that currently and deliberately does not exist.

**Pattern two: write a later row stamped event 1, removed.** This is address_table's design and credential_table inherited the vocabulary in its column comment. Exactly one function in the codebase writes such a row, `addressRemoved`, and nothing calls it — so the pattern is documented in two schemas and practiced in none. What it buys is that a removal becomes a first-class fact with the full margins around it: its own row_tag and row_tick, so the when is recorded, and room for whatever else the table's margins carry. What it costs is interpretation on every read — the collapse rule grows a knockout step, exactly as the old comment worked out, where a 1 wipes itself and everything earlier before you go looking for a 4 and then a 3.

**Pattern three: set hide to nonzero.** This is what actually runs. `queryHide` flips `hide` from 0 to a nonzero value, and level3 calls it at eleven sites, all on credential_table, behind every `credentialXxxRemove`. It is cheap and total — one UPDATE can retire a whole lifecycle. What it costs is context: `hide` is a flag rather than a timestamp, so the when is not recorded, and neither is the browser or the IP that initiated it. Hidden rows survive in the table but are reachable only through the two counting helpers, since every read helper filters `hide = 0`.

Four details make the picture messier than the three-way choice suggests, and each is worth carrying into whatever sprint settles this.

**A note in address_table's own scaffolding doubted that one rule fits every table.** Thinking through the two lookup functions, it asked directly — "are we hiding rows here? maybe for this one, which is lower churn than signing in, we dont" — proposing that the right answer varies with how often a table churns. A table written once per address behaves nothing like one written on every sign-in, and the cost of keeping retired rows around scales with the difference. So the standardization has a prior question to answer before it picks a pattern: is it choosing one rule for the whole schema, or a rule for choosing, applied table by table? The house instinct runs toward one rule everywhere, and this note is the one recorded argument against it.

`queryHide` takes a `hideSet` option that defaults to 1, so a vocabulary of different nonzero hide values — different reasons for hiding — was anticipated in the helper's design. No caller passes it, so the vocabulary is unused and undefined.

Within credential_table, "remove" already means two different scopes depending on the type, and nothing states the rule. `credentialOtpRemove` hides every row about the address, proven or pending, so a removed address doesn't linger looking half-finished. Wallet, oauth, name, password, totp, and browser removals hide only the event-4 rows, leaving mentions and challenges visible. `credentialCloseAccount` hides event 4 across every type and deliberately leaves event-3 challenges standing as an audit trail. All three behaviors are defensible; none of them is written down as a rule a reader could predict.

And a fourth pattern is already practiced on one table, which is worth naming because it changes the shape of the eventual standardization. settings_table edits in place: `settingWrite` calls `queryUpdateCells`, an UPDATE on the cell itself, with no new row and no hide. So the codebase is not purely ledger-style today — it is ledger-style everywhere except the one table where a setting simply changes.

The broader version of this question — ledger versus edit-in-place with a paired audit table — is the subject of ledger.md, and it is the higher-cost half. The narrow removal question above can be settled first and independently, and it should be, because it is the one the cleanup keeps bumping into. What this sprint owes the later one is simply not to delete the evidence: `addressRemoved` and address_table's event vocabulary are the clearest surviving statement of pattern two anywhere in the repository, and once they are gone this section is the only record that the pattern was ever the plan.

## service_table: the design, as the notes have it

**The shape.** Eighteen columns. Beyond the margins: `browser_hash` and `user_tag` for who was there, `event_text` for what happened, the address block as `type_text` plus the same three forms, then the provider block as `provider_text`, `service_text`, `request_text`, `response_text`, `error_text`, and finally three spare slots as `note1_text` through `note3_text`. Two indexes mirroring address_table's: by user, and by type and normalized address.

**The idea,** from the notes file: a history and audit of every request and every response to every API, so you can see what worked and what didn't, how quickly the API responded, and how quickly the user was able to complete the task related to the API — with the instruction to start recording this information even before there is a system that uses it.

**The essay under the table** adds the detail. This table is more like a log or a data lake than the others. Records can accumulate long before round robin exists to consult them, and before that a staff page showing that one provider is faster than the other will query from here. It carries both a browser hash and a user tag, because there will be records written just before a person at a browser gets a user tag. `event_text` should be a tag like `Challenged.` or `Validated.`, ideally at the user level — something the user would recognize as a task they started or completed — while accepting that some records will drop to the lower level of just something between the worker and the provider. The design stays granular in the house style: if the provider never responds, that'll be one record without a second record. And it admits its own uncertainty: two indexes as a starting point, with no idea yet how this will be queried, noting that only the queries feeding a live user interaction — like avoiding an emailer that broke an hour ago — need to be fast.

**Round robin is the consumer it was built for.** The robin essay states the two things the system does: if an external API breaks, even silently, robin notices and immediately stops using it; and while several comparable APIs are working, robin knows which one lets users complete tasks fastest. Crucially it does this by watching real users' real interactions rather than synthetic probes. The design notes say the schema is generalized so code can track a new resource and provider just by mentioning it, that percentiles are calculated by Postgres directly rather than in server code, and that short-term and full-history tables together give both moment-to-moment awareness and a lasting record.

**The audit purpose** is named in the four-purposes logging essay as the second of four: verbose documentation of third-party API performance, where the entries are long and contain objects several references deep, with no querying — archival only, for a developer to open later when an API is misbehaving and try to determine the cause. Two ttds then point at this table as the place that content should move to: one saying that logAudit content should be queryable and therefore belongs in service_table rather than Datadog, and one at the end of the table's own essay saying plainly that wherever we currently log an AUDIT to Datadog, we should also write here.

**Where it lives now.** ledger_table is the successor and is a much smaller shape: the same margins for filtering — browser hash, user tag, IP, wrapper hash — plus `action_text`, `event_text`, and `provider_text` naming what happened, and one `json` for everything else, instead of fifteen fixed text columns guessing in advance at what a provider call looks like. credential_table event 3 carries `{provider}` in its note, recording which provider was asked to carry a given code. trail_table carries the challenge lifecycle as hashed facts. delay_table carries user-level task durations as real numeric columns precisely so Postgres can compute the percentiles the robin design wanted.

## What service_table planned that the successors haven't taken up

The message path is genuinely covered. `credentialOtpSend` writes a credential_table event-3 row naming the provider, writes three trail messages recording that the address was bothered and the challenge opened, and then writes a `MessageSent.` ledger row whose note is the entire task object the lambda returned — provider, service, the full parameters, the request we built, the provider's response, any error, and the duration. `credentialOtpEnter` writes trail rows for wrong guesses and for closing the challenge, and an event-4 row on success. Between the three tables, the worked example is chronicled end to end.

Provider failure is covered better than it first looks. `sendMessage` catches provider exceptions into `task.error` and returns normally, so a provider that fails still comes back through the door and still lands a ledger row with the error in it, serialized with name, message, and stack rather than flattened away. What produces no row at all is a failure of our own lambda — then the fetch throws, the door alerts, and the `if (sent)` guard is never true. That is arguably the correct shape, and close to the design's own "one record without a second record," but it is worth stating rather than rediscovering.

**Turnstile is still audited only to Datadog.** The check in level2 calls `logAudit` on failure and writes no ledger row. This is the third of the smaller-dog sprint's three conversions and is held by that sprint's layering decision, since the check lives in level2 and `ledgerAdd` is level3. It is the clearest case of "every request and every response to every API" not being honored.

**The upload path records nothing.** The upload lambda talks to S3 and no audit of any kind is written, in either channel.

**The chain provider records nothing.** Smart-contract wallet verification reaches Alchemy and leaves no trace.

**Robin does not exist, and the page currently picks the provider.** The endpoint takes a single letter from the request body and maps `A` to `Amazon.` and `T` to `Twilio.`, with a ttd at the line saying the round robin system, not the page, should be choosing. Nothing consults history to make the choice. Robin is a real initiative rather than a loose end, so the cleanup does not have to close this — but the deletion should record that robin's data source is now delay_table plus ledger_table, so the plan doesn't come back looking for a table that isn't there.

**The user-completion-time half of robin is unmeasured.** delay_table records exactly one task today, `Hello.`, with three of its five duration slots filled with -1. The design wanted to know how quickly a user completes the task around an API — how long from requesting a code to entering it — and nothing measures that.

**The OTP code itself rides in the ledger note in plaintext.** The task object's parameters carry `subjectText` and `messageText`, and both contain the answer the user is about to type. trail_table deliberately keeps only hashes of its messages; ledger_table keeps the whole task, and the rows never expire. This is not new — the same object already went to Datadog through `logAudit` — but the cleanup is the moment we bless ledger_table as service_table's successor, so what a `MessageSent.` row should hold is fair to settle while doing it. The options are to keep it as is on the grounds that the database already holds full credentials and is secured accordingly, to drop the composed message text and keep the rest, or to keep it under an expiration the way trail rows can carry one.

## How the removal went

Done August 26, 2026, and recorded briefly because the shape is the template for retiring any table nobody uses.

**service_table was the only part that touched the hosted database.** It held zero rows, and the catalogs confirmed nothing pointed at it — no foreign key, no view, no policy — so with no writers there was no dual-write, no backfill, and no read-switch, and the playbook collapsed to a single `DROP TABLE` paired with its registry edit in the same commit. Its three indexes and its grants fell with it. The older RLS migration still names it in an `ALTER TABLE` and a `REVOKE`; that file is history and was not rewritten, and the migration history was already not replayable from an empty database, since ledger_table is the only table a migration file ever created rather than a hand in the dashboard.

**address_table was registry-only, so deleting its `SQL()` block was the whole schema change.** PGlite stopped building it and the drift check lost nothing to explain, which is what registry-only means in practice.

**The registry is now nine tables against the cloud's six,** and the superset is exactly the three sketches — example_table, profile_table, user_table — each still legible as registry-only by carrying no `ENABLE ROW LEVEL SECURITY` line.

**The code that goes with them.** Eight exported functions, none of which reach the icarus barrel: `addressRemoved`, `addressMentioned`, `addressChallenged`, and `addressValidated` over the shared `address_add`, which have working bodies and no callers; `addressToUser` and `userToAddress`, which are comment blocks with no bodies; and `browserChallengedAddress` and `browserValidatedAddress`, which are empty and name both dead tables in their would-be bodies.

**The ttds and essays that point at them.** The in-flow comment in `credentialOtpSend` saying this is where address_table and maybe service_table need taking care of — both jobs are already done by the lines bracketing it. The ttd in level2 saying logAudit content should go to service_table. The line at the end of service_table's essay saying to write here wherever we log an AUDIT. And the essays themselves, per the standing doctrine that finished scaffolding is deleted rather than kept as a museum, with whatever survives moving into this document or into the sprint documents that inherit the work.

**What gets handed off rather than deleted.** Robin's design belongs wherever robin is planned, since its data source changed but its goals did not. The audit-everything requirement belongs to the smaller-dog sprint, which is already converting the last audit site. The removal-pattern question above belongs to whichever sprint standardizes it, and this document holds it until then.
