# data tasks

The queue of data-layer work, each task many turns and the next ones many sessions. The three at the top run in a fixed order, and the order comes from what each proves about the one before it: the smaller dog can only remove Datadog once every change in the system has its record in ledger_table, and we can only be sure those records are complete once the tables have stopped keeping history of their own, because a fact a mutating table loses is lost only to that table and never to the ledger. So the ledgerathon first, then hideless, then the smaller dog. delevelize joined the queue September 14, 2026, and its place is its own first decision: folded into hideless's chapters, or a pass of its own just before them. A new session takes each one, and this document with hideless.md, hidehow.md, delevelize.md, and smaller-dog.md is what it reads to start. Live-table changes ride the proven migration flow — migration.md holds the playbook, each migration file and its SQL() block edit in the same commit, grid tests beside code changes.

## ledgerathon

Done September 13, 2026, over a week from September 7. Every mutation of a live table writes its ledger row from the function that mutates, so no caller can forget: every credential flow, sign-up's three set functions, close account, and the password and totp checks that moved down from the endpoint into level3 so their refusals are on the record. Every dealing with a third party is a pair, Asked. before the call and Answered. after, at the message send and the chain call. ledger_table gained three columns on migration.md's playbook: tag_text for the row's own tag, so an otp challenge or a wallet nonce gathers its rows across the clicks that make them; door_tag, mandatory and minted by the door, so every row names the request that wrote it; and duration, filled by the closing row of every pair. The drift check closed clean at seventeen columns and nine indexes. Rows read the browser hash, the client cells, and the tag from the door in AsyncLocalStorage rather than from threaded parameters. The standing rule from here: a new mutation arrives with its ledger row in the same turn. Left out on the record: turnstile, the upload lambda, settings_table, and the oauth exchange inside @auth/core. The week of soak the plan asked for was set aside September 14, 2026 for a code review of the pair mechanism instead: the open row is awaited before every call and no throw path closes it, so a call that never came back shows as an Asked. row with no Answered., and a failure that did come back shows as a close whose task carries the error. That orphan query is the standing sanity check, and where a timeout of our own would be chosen from if one is ever set. The charter and its rules live in the essays above ledger_table in level3, and the document retired into contents.md.

## hideless

Second, planned September 7, 2026 in hideless.md, and cleared to start September 14 once the ledgerathon's pairs were reviewed in place of a soak. Every table converts to editing cells and deleting rows, and the code around it with them: the hide column leaves every table, credential_table becomes one row per credential held or in flight, and level2 gains the delete and update helpers it was built not to have, on migration.md's playbook with a history backfill and collapse ahead of the code switch. It installs the tidiness rule: outside ledger_table, a table is the shortest possible statement of the system as it exists right now, with no history, and a finished flow leaves its table the moment the code knows. It is also the ledgerathon's proof: once a table deletes what it no longer holds, a mutation that left no ledger row is a loss that shows, where a hidden row would have covered for it. The hosted survey behind it: credential_table holds 292 rows and 221 are hidden, and no other table hides a row.

## delevelize

Framed September 14, 2026 in delevelize.md, a first draft, and not yet placed. Remove the query vocabulary from level2, the helpers named queryGet, queryHide, queryAddRow, and their siblings, so that level3's application functions call supabase-js directly, keeping the grid tests, the adapter, getDatabase as the seam, and in some form still to be decided the three things the helpers give for free: loud failure on a bad cell, margins filled the same way on every insert, and one line that tosses every Supabase error. The layer was written for testing mutations by hand from a checked vocabulary; the cost now is a helper per query shape, looked up on every read and unable to say anything it wasn't written for. The grid adapter models supabase-js rather than the helpers, so a direct call is tested exactly as a helper is. Its place is the open question: hideless's credential chapters rewrite every level3 call anyway, so the draft leans toward folding the conversion into each chapter rather than rewriting every function twice.

## smaller dog

Third, after the ledgerathon and hideless, because Datadog can only leave once every change in the system has its record in ledger_table and hideless has proven those records complete. Shrink the Datadog and logging apparatus to almost nothing, planned in smaller-dog.md. The ledgerAdd conversions that were to lead it are the ledgerathon's now: two are in — the message task writes its Challenged. row, tagged with the address type and the provider, at the worker while the lambda still sends its own audit, and both oauth sites write ledger rows beside the old audit — and the turnstile failure is a special case decided September 7, 2026: not a change to our data, so no ledger row and no layering decision, and this sprint picks its channel between console.error to the Cloudflare dashboard and the one dog that survives, to Datadog. What remains here is the removal pass: the function suite, the double-hulled door catches, the keepPromise parking lot, and the pluggable log sinks leave, and one async dog stays. The document holds the inventory, where each of the old four purposes goes, and the decisions the sprint must make — dog's destination, the attention channel, audit latency.

## proven rename

Done September 6, 2026, in two passes. The first made proven the one word for the moment a user proves control of an address: comments and documents say it, the oauth handler writes Proven. into ledger_table where it wrote Validated., credentialOtpValidated became credentialOtpProven, and one data-only migration, the first of its kind, updated the five ledger rows that said Validated. The second replaced credential_table's numeric event column with event_text holding Mentioned., Challenged., or Proven., on migration.md's full playbook: the expansion added event_text beside event with scaffolding defaults; the dual-write deploy had credentialSet take the tag, check it through a new hasEvent and checkEvent pair, and write both columns; the backfill gave all 262 rows their word, 45 Mentioned., 67 Challenged., and 150 Proven., rehearsed in PGlite first; the read-switch deploy moved every read to the word, with credentialOtpGet's collapse ranking tags through credentialEventRanks; and the contraction dropped the number column and the last default. Four pushes, two deploys, and a drift check clean at eleven columns. The objects the page receives keep the property name event, the way the ledger's JavaScript names its event_text, and hold the word.

## backup plan

Researched and tabled, September 4, 2026, until much later. This was a research task, and the research is done: database-stack.md's backup-plan section records three good approaches — the pg_dump schema-and-data pair the CLI already half runs, the CSV cold copy down the scripts path, and Supabase's plan-gated managed backups — and what they establish is the confidence the sprint was after. We hold a variety of ways to back up, none of them ties us to Supabase as a vendor, and none of them needs the platform's turnkey and expensive options. Nothing waits on the choice, so it stays out of the queue's ordering, and it should not come up again until we deliberately pick it up. What remains for that day is the choosing: which combination, on what cadence, and where the sensitive files sleep, since a held backup is exactly as sensitive as the database — a fourth place secrets live, beside the workstation, the bundles, and the providers' secret services, so whatever encrypts one wants a home in the key system and a tracer family of its own.
