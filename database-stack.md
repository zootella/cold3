# The database stack

How cold3 uses its database, in production and in development — the languages, the protocols, and every path from our code to a table. Reference, not planning: read this to get up to speed on how the pieces fit before working on anything that touches the database.

The production stack is short. A Cloudflare worker secret decrypts the database credentials through the Key() system, trusted server code in the worker holds them, and supabase-js calls over HTTPS to Supabase, where under the hood it's PostgREST and PostgreSQL. Credentials live sealed in the wrapper and in local .env files, never in this repository. The development stack has more parts, and this document maps them.

## The key system: secrets sealed into the wrapper

Application keys live in one local file, .env.keys, which is gitignored and never leaves the workstation in plain form. At seal time, seal.js splits its lines by their tags: a key tagged public is encoded into `wrapper.publicKeys` — necessarily and intentionally public, factory presets and client-side values — and every other key is encrypted with AES-256-GCM into `wrapper.secretKeys`. Both strings ride inside wrapper.js, which ships in every bundle: the lambda, the worker, and the browser page all carry the ciphertext. What separates servers from pages is possession of the one symmetric decrypting key, which lives in exactly three places — the Cloudflare secret store, the AWS environment, and the local .env — and has never been anywhere else. A page holds the sealed string as dead weight it cannot open; a server opens it at the door, and from then on Key() answers by name. Two details are easy to miss: every decrypted value is registered for redaction, so secrets that wander toward a log line are blacked out before writing; and because .env.keys is hashed into wrapper.txt like any other file, a changed key value produces a new wrapper hash — the running version is cryptographic evidence of exactly which secrets it holds, and drift between code and keys is structurally impossible.

Bundling secrets this way instead of spreading them across the Amazon and Cloudflare secrets managers is a deliberate trade. Two dashboards mean two places to update, two sets of rules about key counts and value lengths, and real failure modes we hit early: a deploy relying on a new key while the manager still held the old one, or values drifting between platforms, or between local and deployed. A varied, complex system that looks more secure can be less secure, because mistakes become easier than attacks. Here there is a single highly sensitive value that never changes version to version, and each sealed version carries an unconstrained number of secrets whose integrity the wrapper hash proves. For this database specifically, both Supabase values — the project URL and the service key — are sealed as secrets: neither appears in the repository, in any built bundle in plain form, or in the browser at all.



## One language, and the layers around it

Four distinct things stack up here, and naming them separately dissolves most confusion about "how does my JavaScript become a database row."

**SQL** is the only language PostgreSQL understands. Every path below eventually becomes SQL text executed by the server; the paths differ in where that SQL gets written and by whom. SQL has two vocabularies worth telling apart: **DML, data manipulation language** — SELECT, INSERT, UPDATE, DELETE, the row verbs — and **DDL, data definition language** — CREATE, ALTER, DROP, the schema verbs. The distinction matters because our paths differ in which vocabulary they can speak.

**The Postgres wire protocol** is the binary TCP conversation (classically port 5432) between any Postgres client and the server. It is not a query language — it's the envelope: an authentication handshake, then messages carrying SQL text and bound parameters in, then typed row data streaming back. It carries SQL the way HTTP carries a request body. Anything that speaks it is a "Postgres client," and anything that does has the full language — both vocabularies, limited only by the credentials it authenticated with.

**PostgREST's HTTP grammar** is the narrow layer Supabase wraps around the wire. PostgREST runs beside the database and exposes tables as REST endpoints: a request like `GET /rest/v1/some_table?hide=eq.0&order=row_tick.desc` is its own small language meaning "select these rows." PostgREST translates that grammar into SQL and executes it over the wire protocol — it is itself a Postgres client acting on your behalf. Its vocabulary is deliberately DML only: select, insert, update, delete, call a function. **There is no URL that means ALTER TABLE.** That's not a permissions rule — the language cannot say it. This is an anti-footgun measure you can build a team on: code that goes through PostgREST can still delete every row (deletion is DML), but the drop-the-table footgun isn't on the belt at all.

**supabase-js** is not a protocol — it's the JavaScript convenience for building those HTTP requests. `.from('example_table').select('*').eq('hide', 0)` never becomes SQL in your JavaScript; it becomes an HTTPS request, and PostgREST on the far side turns the request into SQL. The one place in our stack where JavaScript does generate SQL directly is the grid-test adapter, which does locally what people assume supabase-js does remotely.

## Every path from our code to a table

**The worker, local and deployed.** The same code, same supabase-js module, same sealed Key() credentials, whether running under `pnpm local` on a workstation or deployed on Cloudflare's real workers — local development talks to the real hosted database on purpose. Chain: JS builder → HTTPS in PostgREST's grammar → PostgREST translates → SQL over the wire → hosted Postgres. Full reach over rows in every table; cannot utter DDL.

**One-off Node scripts.** The identical chain with one more consumer: a script loads .env, decrypts the wrapper's sealed secrets, and uses the same level2 query helpers the application uses. This is the lightest way to answer "what's in this table right now" from a terminal or a chat — zero new moving parts, read-only by the calls it makes, and the results come back through house conventions (hide-filtered, newest first). Chosen over the CLI for ad-hoc reads because the CLI has no query verb at all — see below.

**Grid tests.** No Supabase, no network, no credentials, no protocols. grid() cases call the same level2 helpers, but in simulation mode the adapter intercepts the builder calls, generates SQL text itself in JavaScript, and hands it as a function call to PGlite — Postgres compiled to WASM, living inside the Node process, its tables built from the same SQL() schema registry that mirrors production. Real Postgres semantics with zero moving parts. This is our deliberate lightweight alternative to Supabase's intended heavyweight local flow (`supabase start`, a full local Supabase in Docker containers — Postgres, PostgREST, auth, storage, a local Studio). That full local stack exists on the shelf if we ever outgrow this; so far, PGlite plus the adapter tests whole user flows expressively and fast, without it.

**The dashboard.** Browser login to Supabase's web app, with table views to click through and a SQL editor where you write SQL yourself — both vocabularies, full privileges, human hands. Every cold3 schema change took this path until the CLI arrived; it remains the right tool for ad-hoc human browsing and one-off inspection.

**The supabase CLI, no Docker.** One Go binary, two conversations. For platform operations (login, link, list projects) it speaks HTTPS to Supabase's management API using the personal access token from `supabase login` — credentials to Supabase-the-platform, not to any database. For database operations (`db push`, `migration list`) it asks the management API to mint short-lived Postgres credentials on the spot ("Initialising login role..." — no database password is ever typed or stored), then speaks the wire protocol itself, through a Postgres driver compiled into the binary. You write plain SQL in timestamped migration files under supabase/migrations; the CLI delivers your text verbatim over the wire and keeps the bookkeeping — which files exist locally, which are recorded as applied in the server's history table, `--dry-run` to compare the two. Full language, both vocabularies: this is the migration path, and DDL needs no Docker.

**The supabase CLI, with Docker.** The same binary, summoning tools it doesn't contain. pg_dump and its siblings are compiled C programs that ship with Postgres itself and behave version-sensitively, so for `db dump`, `db pull`, and `db diff` the CLI runs them inside the supabase/postgres image matching the server's exact version — borrowed for a few seconds rather than brew-installed and forever version-matched by hand. Inside the container, pg_dump speaks the ordinary wire protocol to the hosted database, reads the system catalogs with ordinary SQL, and emits its findings as SQL text. Nothing is written by hand on this path; it reads and serializes — schema, data, or both. Docker also holds the psql client, the terminal route for ad-hoc SQL if the dashboard ever isn't enough.

## Choosing a path

- **Read or write rows, ad hoc**: a one-off script down the app's own path, or the dashboard. Not the CLI — its verb set is migrations and platform bookkeeping; it has no "run this SELECT" command.
- **Change schema**: a migration file, pushed by the CLI — no Docker involved. The paired rule: the migration file and the matching SQL() registry edit land in the same commit, so the registry mirrors production at every point in git history.
- **Copy or introspect schema**: the CLI with Docker awake — `db dump`, then compare against the SQL() registry (the drift check).
- **Test flows**: grid tests on PGlite — no database stack at all.
- **Browse as a human**: the dashboard.

The compact truth underneath all of it: there is one language, SQL, and one full-power transport, the wire protocol. The application's path deliberately wraps both in a narrow REST grammar that can't say anything dangerous; the dashboard and the CLI hand you the full language directly; Docker appears only when a version-exact compiled tool has to do the talking; and PGlite is the whole server folded into a library so tests can skip every network hop. Migration files, dashboard SQL, pg_dump output, the SQL() registry, and what PostgREST generates from your JavaScript — all of it converges on the same SQL arriving at the same engine.

## Row-level security: the advisor, the audit, and the planned hardening

Supabase mails recurring warnings — "critical issue," "table publicly accessible," "anyone with your project URL can read, edit, and delete all data" — from a static lint rule that fires whenever a table in the public schema has row-level security (RLS) disabled. The warning is written for a specific architecture; whether it describes a real gap for us was a question to audit, not assume, and the audit's answer changed how we hold this.

Every Supabase project exposes PostgREST at the project URL, and requests authenticate as one of a few built-in Postgres roles. The anon key is meant to ship inside client-side JavaScript — public by design — and authenticates as the restricted `anon` role; `authenticated` is its signed-in counterpart; the service key authenticates as `service_role`, which carries the BYPASSRLS attribute and ignores RLS entirely. In Supabase's primary architecture the browser talks straight to the database with the anon key in the page, and there RLS is the only thing between a deliberately-public key and the data: no RLS means anyone who views source can read and write every table. The advisor exists because scans keep finding live apps in exactly that state.

cold3 is the other architecture, and it is the right one here: untrusted page code never talks to Supabase. Only trusted worker code does, authenticating as `service_role` with the sealed service key, standing as the sole validator between the untrusted page above and the pristine data below. Workers are fast, cheap, and tamper-proof, so letting the browser reach the database directly would add complexity for no real saving. The anon key has never shipped, never been referenced in code, and never left the dashboard.

What the audit found (checked live with `supabase db query --linked`):

- **RLS is disabled on all six tables** (credential, delay, hit, service, settings, trail).
- **The `anon` and `authenticated` roles hold full grants** — SELECT, INSERT, UPDATE, DELETE, plus TRUNCATE and REFERENCES — on every table, credential_table included. This is Supabase's historical default for tables created before the auto-expose behavior changed.
- **`service_role` and `postgres` carry BYPASSRLS; `anon` and `authenticated` do not.**

The honest reading: the app is safe today, but on a single wall. The service-key architecture means the only credential the app ever uses already has proper access, and the anon key — which with these grants and no RLS would give its holder full read, write, and delete over every table, credential data included — is simply a secret that has never left the dashboard. That is genuine protection: the URL alone gets a 401, and the anon key is an unshipped secret independent of the URL. But there is no second barrier behind it. The thing meant by "defense in depth" — something that still holds if the first secret leaks — is the piece that is missing. The advisor is not wrong; it names a real latent gap, gated behind a secret we have kept.

The planned hardening closes it, monolithically, with no per-row complexity:

- **Enable RLS on all six tables, with zero policies.** RLS-enabled-with-no-policy is default-deny in Postgres, so `anon` and `authenticated` can touch nothing, while `service_role` bypasses RLS and continues unchanged (verified: it carries BYPASSRLS, so the worker, local development, and read-only scripts are untouched, and PGlite grid tests run as the table owner and never notice). No new role is created — the "one trusted identity with full access" already exists as `service_role`. This is the move that clears the advisor and ends the emails, because the advisor checks RLS state specifically.
- **Optionally revoke the anon/authenticated grants** as a second layer. Stripping their privileges leaves the roles present (PostgREST needs them to exist) but powerless — safe because cold3 uses neither. This supplements the RLS enable rather than replacing it: on its own, revoking would secure the data but would not clear the advisor, which looks at RLS state and not grants.

Two boundaries on the plan. We cannot un-expose the public schema from the API — the most total "anon off" — because our own worker rides PostgREST with the service key, so the REST surface over public must stay on. And TRUNCATE is the one grant RLS does not cover (it is table-level, not row-level), but it is unreachable through a leaked anon key anyway, since PostgREST offers no TRUNCATE verb; the optional REVOKE closes even that theoretical remainder.

Sequenced as the first migration of the data sprint — a real gap-closer that doubles as a zero-risk rehearsal of the migration-new-then-push flow before hit_table — with the SQL() registry noting the RLS state in the same commit, so the drift check holds us to it.
