# The database stack

How cold3 uses its database, in production and in development — the languages, the protocols, and every path from our code to a table. Reference, not planning: read this to get up to speed on how the pieces fit before working on anything that touches the database.

The production stack is short. A Cloudflare worker secret decrypts the database credentials through the Key() system, trusted server code in the worker holds them, and supabase-js calls over HTTPS to Supabase, where under the hood it's PostgREST and PostgreSQL. Both Supabase values — the project URL and the service key — are sealed as secrets through the key system xray.md documents: neither appears in the repository, in any built bundle in plain form, or in the browser at all. The development stack has more parts, and this document maps them.

## One language, and the layers around it

Four distinct things stack up here, and naming them separately dissolves most confusion about "how does my JavaScript become a database row."

**SQL** is the only language PostgreSQL understands. Every path below eventually becomes SQL text executed by the server; the paths differ in where that SQL gets written and by whom. SQL has two vocabularies worth telling apart: **DML, data manipulation language** — SELECT, INSERT, UPDATE, DELETE, the row verbs — and **DDL, data definition language** — CREATE, ALTER, DROP, the schema verbs. The distinction matters because our paths differ in which vocabulary they can speak.

**The Postgres wire protocol** is the binary TCP conversation (classically port 5432) between any Postgres client and the server. It is not a query language — it's the envelope: an authentication handshake, then messages carrying SQL text and bound parameters in, then typed row data streaming back. It carries SQL the way HTTP carries a request body. Anything that speaks it is a "Postgres client," and anything that does has the full language — both vocabularies, limited only by the credentials it authenticated with.

**PostgREST's HTTP grammar** is the narrow layer Supabase wraps around the wire. PostgREST runs beside the database and exposes tables as REST endpoints: a request like `GET /rest/v1/some_table?hide=eq.0&order=row_tick.desc` is its own small language meaning "select these rows." PostgREST translates that grammar into SQL and executes it over the wire protocol — it is itself a Postgres client acting on your behalf. Its vocabulary is deliberately DML only: select, insert, update, delete, call a function. **There is no URL that means ALTER TABLE.** That's not a permissions rule — the language cannot say it. This is an anti-footgun measure you can build a team on: code that goes through PostgREST can still delete every row (deletion is DML), but the drop-the-table footgun isn't on the belt at all.

**supabase-js** is not a protocol — it's the JavaScript convenience for building those HTTP requests. `.from('example_table').select('*').eq('hide', 0)` never becomes SQL in your JavaScript; it becomes an HTTPS request, and PostgREST on the far side turns the request into SQL. The one place in our stack where JavaScript does generate SQL directly is the grid-test adapter, which does locally what people assume supabase-js does remotely.

## Every path from our code to a table

**The worker, local and deployed.** The same code, same supabase-js module, same sealed Key() credentials, whether running under `pnpm local` on a workstation or deployed on Cloudflare's real workers — local development talks to the real hosted database on purpose. Chain: JS builder → HTTPS in PostgREST's grammar → PostgREST translates → SQL over the wire → hosted Postgres. Full reach over rows in every table; cannot utter DDL.

**One-off Node scripts.** The identical chain with one more consumer: a script loads .env, decrypts the wrapper's sealed secrets, and uses the same level2 query helpers the application uses. Zero new moving parts, read-only by the calls it makes, and the results come back through house conventions (hide-filtered, newest first). In practice, though, most needs resolve to this path's neighbors, and the sorting rule is about repetition: a peek at live data — a sanity check, an answer to a question in chat, confirming what the dashboard shows — is naturally one-off and belongs to `db query` below, which is terser; and a verification worth keeping around to run again isn't a script at all — it's a grid test, which is exactly what the grid suite is for. What's left for a script is the rare question that needs the app's own eyes on the live database — supabase-js and PostgREST in the loop against real hosted rows, which grid tests deliberately never touch — or an ad-hoc write that should pass through the house checks.

**Grid tests.** No Supabase, no network, no credentials, no protocols. grid() cases call the same level2 helpers, but in simulation mode the adapter intercepts the builder calls, generates SQL text itself in JavaScript, and hands it as a function call to PGlite — Postgres compiled to WASM, living inside the Node process, its tables built from the same SQL() schema registry that mirrors production. Real Postgres semantics with zero moving parts. This is our deliberate lightweight alternative to Supabase's intended heavyweight local flow (`supabase start`, a full local Supabase in Docker containers — Postgres, PostgREST, auth, storage, a local Studio). That full local stack exists on the shelf if we ever outgrow this; so far, PGlite plus the adapter tests whole user flows expressively and fast, without it.

**The dashboard.** Browser login to Supabase's web app, with table views to click through and a SQL editor where you write SQL yourself — both vocabularies, full privileges, human hands. Every cold3 schema change took this path until the CLI arrived; it remains the right tool for ad-hoc human browsing and one-off inspection.

**The supabase CLI, no Docker.** One Go binary, two conversations. For platform operations (login, link, list projects) it speaks HTTPS to Supabase's management API using the personal access token from `supabase login` — credentials to Supabase-the-platform, not to any database. For database operations (`db push`, `migration list`) it asks the management API to mint short-lived Postgres credentials on the spot ("Initialising login role..." — no database password is ever typed or stored), then speaks the wire protocol itself, through a Postgres driver compiled into the binary. There is also an ad-hoc query verb — `supabase db query --linked` runs arbitrary SQL against the hosted database, riding the management API end to end rather than minting a login role — full SQL that reaches the system catalogs, grants, and role attributes PostgREST cannot see. You write plain SQL in timestamped migration files under supabase/migrations; the CLI delivers your text verbatim over the wire and keeps the bookkeeping — which files exist locally, which are recorded as applied in the server's history table, `--dry-run` to compare the two. Full language, both vocabularies: this is the migration path, and DDL needs no Docker.

**The supabase CLI, with Docker.** The same binary, summoning tools it doesn't contain. pg_dump and its siblings are compiled C programs that ship with Postgres itself and behave version-sensitively, so for `db dump`, `db pull`, and `db diff` the CLI runs them inside the supabase/postgres image matching the server's exact version — borrowed for a few seconds rather than brew-installed and forever version-matched by hand. Inside the container, pg_dump speaks the ordinary wire protocol to the hosted database, reads the system catalogs with ordinary SQL, and emits its findings as SQL text. Nothing is written by hand on this path; it reads and serializes — schema, data, or both. Docker also holds the psql client, the terminal route for ad-hoc SQL if the dashboard ever isn't enough.

## Choosing a path

- **Read rows or inspect state, ad hoc**: `supabase db query --linked` — full SQL, aggregates, the system catalogs, hidden rows included, one reviewable command with zero setup; a peek is naturally one-off, and this is the one-off tool. The dashboard to browse as a human. A one-off script only for the rare question that needs the app's own eyes on live rows — and if the answer is worth checking twice, it isn't a script, it's a grid test.
- **Write rows, ad hoc**: a one-off script through the app's own helpers, so the checks run; or the dashboard, with human hands.
- **Change schema**: a migration file, pushed by the CLI — no Docker involved. The paired rule: the migration file and the matching SQL() registry edit land in the same commit, so the registry mirrors production at every point in git history.
- **Copy or introspect schema**: the CLI with Docker awake — `db dump`, then compare against the SQL() registry (the drift check). Match columns by name, not by position: the registry orders them for legibility while the cloud keeps them in the order they were added, and column order carries no meaning because nothing here reaches a column positionally. Column order inside an index or constraint is a different matter and must match exactly.
- **Test flows**: grid tests on PGlite — no database stack at all.
- **Browse as a human**: the dashboard.

The compact truth underneath all of it: there is one language, SQL, and one full-power transport, the wire protocol. The application's path deliberately wraps both in a narrow REST grammar that can't say anything dangerous; the dashboard and the CLI hand you the full language directly; Docker appears only when a version-exact compiled tool has to do the talking; and PGlite is the whole server folded into a library so tests can skip every network hop. Migration files, dashboard SQL, pg_dump output, the SQL() registry, and what PostgREST generates from your JavaScript — all of it converges on the same SQL arriving at the same engine.

## Row-level security: the advisor, and the two walls in place

Supabase mails warnings — "critical issue," "table publicly accessible" — from a static lint rule that fires whenever a table in the public schema has row-level security (RLS) disabled. The warning is written for a specific architecture, and the roles model explains it: every Supabase project exposes PostgREST at the project URL, and requests authenticate as one of a few built-in Postgres roles. The anon key is meant to ship inside client-side JavaScript — public by design — and authenticates as the restricted `anon` role; `authenticated` is its signed-in counterpart; the service key authenticates as `service_role`, which carries the BYPASSRLS attribute and ignores RLS entirely. In Supabase's primary architecture the browser talks straight to the database with the anon key in the page, and there RLS is the only thing between a deliberately-public key and the data — the advisor exists because scans keep finding live apps in exactly that state.

cold3 is the other architecture, and it is the right one here: untrusted page code never talks to Supabase. Only trusted worker code does, authenticating as `service_role` with the sealed service key, standing as the sole validator between the untrusted page above and the pristine data below. Workers are fast, cheap, and tamper-proof, so letting the browser reach the database directly would add complexity for no real saving. The anon key has never shipped, never been referenced in code, and never left the dashboard — genuine protection, but on its own a single wall, because Supabase's historical default handed `anon` and `authenticated` full grants on every table, which would make a leaked anon key full read and write. Defense in depth wants a barrier that still holds if the first secret leaks, and two are in place, monolithic, with no per-row complexity:

- **RLS is enabled on all six tables, with zero policies.** RLS-enabled-with-no-policy is default-deny in Postgres, so `anon` and `authenticated` can touch nothing, while `service_role` bypasses RLS — the worker, local development, and read-only scripts run unchanged, and no new role was needed, because the "one trusted identity with full access" already exists as `service_role`. The advisor checks RLS state specifically, so this is the wall that keeps `supabase db advisors --linked` quiet and the emails away.
- **The anon and authenticated grants are revoked.** The roles remain — PostgREST needs them to exist — but hold no privileges. This second layer also closes TRUNCATE, the one grant RLS cannot cover (it is table-level, not row-level), though a leaked anon key couldn't reach it anyway: PostgREST offers no TRUNCATE verb.

One boundary shaped this design: we cannot un-expose the public schema from the API — the most total "anon off" — because our own worker rides PostgREST with the service key, so the REST surface over public must stay on. And the registry mechanics: the SQL() registry carries the literal ENABLE ROW LEVEL SECURITY lines, harmless in PGlite because grid tests connect as the table owner, and owners are exempt from row-level security unless it is specifically forced — which we never do. The REVOKE is the one statement the registry text cannot hold: PGlite has no anon or authenticated roles to revoke from, and would error executing it, so that line lives only in the migration file.

One known remainder, small and optional: the default privileges in the public schema still auto-grant anon and authenticated full access on any table created later through the dashboard — visible at the bottom of a schema dump as ALTER DEFAULT PRIVILEGES lines. The six existing tables are covered by the REVOKE, so nothing is exposed today; a one-line ALTER DEFAULT PRIVILEGES ... REVOKE migration, riding along with some future push, would close the door for tables that don't exist yet.

## Backup plan

A bookmark, not a build: nothing in this section exists yet. Today the database has no backups beyond whatever the project's Supabase plan provides automatically, and the rows are history a rebuild could not recreate. Three approaches follow, each protecting against a different kind of loss. They compose rather than compete, so a later epic decides which, or which combination, and on what cadence.

**Supabase's managed backups** are the platform doing the work, gated by plan. The Free tier gets no automated backups at all — Supabase's own docs there advise manually exporting with the CLI, which is the second approach below. The Pro tier gets daily backups with seven days of retention (Team fourteen, Enterprise up to thirty), and Point-in-Time Recovery is a paid add-on that archives write-ahead-log files every two minutes, letting a restore land within about two minutes of any chosen moment. Restores run from the dashboard, with the project inaccessible while one runs, and on newer projects the platform's backups are physical files that cannot be downloaded. So this approach is protection you rent rather than a file you hold: it covers platform-side loss and our own bad writes, back to a restore point, with zero code — and provides nothing you can carry offline or out of the vendor.

**The pg_dump pair** is the intended portable way, and half of it already runs: the drift check's `supabase db dump --schema public` is the schema half. The data half is one more command, `supabase db dump --data-only --use-copy -f data.sql`. Both ride the CLI's Docker path — pg_dump borrowed at the server's exact version, minted login role, no password — and pg_dump reads inside a single transaction snapshot, so the file is consistent even with live traffic writing mid-dump. The pair is a complete logical backup that restores into any Postgres anywhere with plain psql — another Supabase project, a container, a laptop — which makes it the vendor exit door as well as a backup. Cost is one command and a few seconds; coverage is every table and every row, though not platform configuration or the CLI's migration history table, whose real record is the repo's migration files anyway.

**The CSV cold copy** is one file per table, readable by nearly anything. Our conventions make this unusually clean: every cell is bigint, char, text, or jsonb — no dates, no UUIDs, no arrays — so CSV loses nothing, and a json cell rides as quoted JSON text inside its field. The house-style implementation is a small read-only script down the scripts path, selecting every row of every table — hidden rows included, unlike the house read helpers, so the copy is complete — ordered by row_tick and printed with the column titles as the header row, standard quoting handling commas and newlines. Stable order makes successive exports diffable, and the tables are small enough (the largest holds a few thousand rows) that the whole export takes seconds. Coverage is rows only, with the shape documented by the header row and the SQL() registry; restoring means a script or Postgres COPY FROM, slower and more manual than psql replaying a dump. What it uniquely provides is legibility and longevity: it opens in a spreadsheet, parses in any language, and remains readable if Postgres, Supabase, and this codebase are all long gone.

One caution binds the second and third approaches: a backup file is exactly as sensitive as the database, credential_table riding in full. Any held copy — data.sql or the CSVs — is a key, not a document: encrypted at rest, stored where secrets live, never in the repository.
