# hidehow

The battle plan for the hideless sprint. hideless.md is the mission brief: why hiding was a mistake, the rules every table follows after, the shape of credential_table after, and the decisions. This document is the tactics beneath it: the chapters, a menu we pick from, each one a table, or for credential_table a credential type, with what the code around it does today and what changes. We burn it down as we go. A chapter gains detail as we plan it, and leaves the document when its work lands; when the last one leaves, so does the document.

Three acts, and only their edges are ordered. **The new query helpers** came first and are in: level2 has queryUpdate, which edits the rows a where object finds with the cells a set object names, and queryDelete, which removes the rows a filter finds, hidden or not, and the prose that stated the old rule now states the new one. **The tables and types** in the middle, a menu: the tables that never used hide are done, one migration on September 14, 2026 having taken the column out of them and out of level2, and each credential type converts its code from hiding rows to editing and deleting them, its hidden rows leaving the hosted table along the way, in whatever order we choose. **The column drop** last, credential_table's own, once its last type converts.

level2 no longer filters or fills hide anywhere. credential_table alone still has the column, and carries the filter itself: its reads go through credentialRows, one function in level3 that adds hide: 0 to whatever cells it is given, and credentialSet writes hide: 0 in the row it inserts, so the filter lives in two lines rather than in every helper, and both leave with the column at credential_table's own drop. queryHide stays until then too, since it only ever touched this table. What converts chapter by chapter is the meaning of rows and the code that writes and reads them. credential_table goes type by type rather than as one table because the patterns vary by type: Browser. stacks rows and the newest wins, Name. hides the old row and appends a new one, Email. and Phone. rank the stages and the highest wins. Each type has its own function family, its own grid tests, and its own removal scope.

Every credential type's chapter has the same shape, and it is a code chapter: one commit and one deploy, with no push. Read the code around the type completely, and write what it does into its section here. Then three jobs, and a chapter is done only when all three are. Convert its writers to edit and delete and its readers to a lookup. Check every ledger row the type writes: one beside every mutation and every refusal that deserves one, carrying what the charter above ledger_table says it should and never a secret, and reading sensibly beside the table change it records. And audit the type's grid tests against the standard testing.md sets, the happy path, the sad paths, the mildly chaotic ones like a stale tab or a repeated click, and the plausible attacks, adding what is missing and asserting exact row counts, hidden or not, so a hide can never pass for a delete. The manual smoke that follows confirms the wire and the real data; it is never the place a mistake in the application logic gets found, because that is the tests' job. Two rules hold the window between a chapter and the column drop at the end. Every update a converted type makes names hide: 0 in its where clause, so an old hidden row is never edited, while a delete names none, since a user's row deleted by identity should take a hidden old one with it. And a reader that stops ranking asks for its stages by name, Proven. and Challenged., so a stale Mentioned. row still standing from before the cleanup is never listed. Smoke the type's panel. Move on. The hidden rows and the superseded visible rows leave at the end, all at once, and no ledger rows are written for them, decided September 14, 2026: a row invented from a hidden row would break the ledger's charter several ways, a borrowed tick, no honest build to name, and a snapshot of the table rather than a record of an act, and wrapper_hash already tells a reader which builds wrote no rows.

The groups below are sorted by difficulty, and that is all the order they carry. This is a menu: pick a section from anywhere, edit it as its work is planned and as the work teaches more, and remove it when its work lands.

**credential_table.** How a user can sign in, and whether what they just said is valid to sign them in. Today it is the one table built fully in the ledger style: one row per event in a credential's life, Mentioned., Challenged., or Proven., written by the one writer credentialSet, and read by a family of functions per type that each interpret the rows. The snapshot attachState assembles for the credential panel runs one of those reads per type on every Get. and after every action. The columns: the three margins, user_tag, type_text, event_text, the f triad, hash_text, and json. Every index on it leads with hide. Every queryHide site in the code is on this table. Beside the per-type functions stand credentialCloseAccount, the one cross-type mutation, which hides every Proven. row of the user in one call and leaves the Challenged. rows standing, and under the rules after the sprint deletes every credential row of the user, converted in whichever chapter first needs it or as a small pass of its own; and credentialGet, an exported stub with no body. credentialEventRanks ranks the stages for the otp reader, and hasEvent and checkEvent guard the stage words at the writer. The hosted survey of September 7, 2026 found about three hundred rows, three quarters of them hidden, and a few dozen expected after the conversion: one per session, name, password, totp enrollment, wallet, oauth link, and proven address, plus whatever is in flight. Its types are the chapters of the next three groups, and its own column drop is the last act, once the last of them converts, in the three steps the tables that never used hide walked. First a survey of the hosted rows, read-only: group by type, stage, hide, and identity, and list the winner per identity by the rule today's readers apply, with the counts going into the migration file's header as the record of what leaves. Then one push that deletes every hidden row and every visible row that isn't its identity's winner, creates the unique indexes the conversion earned, one holder per address, one session per browser, one name, one password, and one totp per user, and one account per oauth identity, sets a scaffolding default on hide, and rebuilds credential_table's own indexes without the column under the next numbers. Then the deploy that drops the filter from credentialRows and the explicit zero from credentialSet, retires queryHide, and removes hide: 0 from every converted update's where clause. Then the contraction that drops the column, and the drift check. The document sweep rides with it: database-stack.md's shape section describes two margins and a row that leaves by deletion, tables.txt's definition of hide goes, data-cleanup.md's three-patterns section leaves with the question it sized, credential.md's hide-does-the-work section describes what runs, testing.md notes the adapter's delete branch is reached, and migration.md gains the paragraph on a change of row meaning.

One question the finished migration left open: whether trail_table's expiration becomes real. Every production writer leaves it at zero, keep forever. hideless.md has the writers set it per message and a housekeeping sweep delete rows past it, while tables.txt's own note argues that the index ending in row_tick makes old rows cheap to ignore and deletion unnecessary. The sweep, if built, is the same job that removes the challenges nobody came back to, so the question belongs with whichever credential chapter first needs the sweep.

# Involved

A flow in flight rides a Challenged. row beside the Proven. row a finished one leaves. Today the flow's last step inserts the proof and hides the challenge, or hides nothing at all, and abandoned starts stand until something hides them by accident. After, the challenge row is edited to Proven. in place when the flow finishes, deleted the moment the flow knows it is over, and left to the sweep only when nobody came back. These chapters teach the edit of a stage in place, the delete at every exit of a flow, and, for oauth, a challenge written and closed from a file outside level3.

## Oauth.

Two kinds of row, written from two files. The oauth handler under the lite door writes a Challenged. row with the provider in json when a signed-in user starts a flow at the signin path, before @auth/core runs. Its signIn callback, once the provider answers, calls credentialOauthSet, which runs two read checks, this user has no account with this provider yet and no other user holds this identifier through credential15, and inserts the Proven. row: provider, identifier, handle, name, and the whole proof in json, and the provider's email in the f triad when it gave one. A cancel or an error at the provider writes a Cancelled. ledger row and nothing here. Get lists the user's Proven. rows filtered to the configured providers. Remove hides the Proven. row by user and provider. Grid tests cover linking and re-linking, the cross-user identifier claim, the shape of the note, and the planner choosing credential15, whose EXPLAIN spells hide = 0 in its text.

**Hidden today:** yes, by Remove, plus close account. Never hidden: every Challenged. row, since no path closes one when its flow finishes, a couple dozen of them visible on September 7; and one hidden row typed Discord. from before the oauth types unified. After: the callback edits the challenge to Proven. or deletes it on a refusal, the cancel path deletes it through a level3 call, only a flow nobody returns from waits for the sweep, Remove deletes, and credential15 becomes unique among Proven. rows.

**The chapter.** The start deletes any earlier challenge of this user's for the provider and inserts the new one, one challenge per provider in flight, and writes its ledger row for every start, signed in or not, with a blank user when nobody is, so a proof always has a start behind it and a signed-out start is itself on the record. The callback's Set edits the challenge into the proof, writing Proven., the provider's details, and its email together, and refuses as Expired. when the signed-in user has no live start for the provider, since the state cookie binds the flow to the browser and the challenge binds it to the person, which is what stops a stranger's start at a shared computer from linking their account to hers; a refused callback deletes the challenge beside its Refused. row. A new level3 function takes the cancel: it deletes the user's challenge for the provider when the handler knows both and writes the Cancelled. row either way, so the handler stops writing that row itself and resolves the signed-in user once, before the flow, for every request. Remove deletes every Oauth. row of the user's for the provider. Get and both checks stay. The tests gain a flow test: one challenge per provider, the proof as the challenge's own row, a refusal and a cancel each deleting the challenge, a cancel after the proof leaving it standing, and a signed-out start recorded in the ledger alone.

# Hard

One family serving both address types, with the most reading logic in the table and the largest test surface. An address has stages and a read ranks them, a proof and a live challenge for the same address may both stand, a resend replaces a challenge, and the trail beside the table carries the answer and the counts. This is the chapter where the rank map, the grouping, and the mentions all leave, and where the snapshot's projection of live challenges rides.

## Email. and Phone.

One family with a type parameter. Send checks the holder, counts the trail for the permit, writes a Mentioned. row with the outcome when it refuses and without one when a code goes out, composes the code, sends it through the lambda inside a ledger pair, hides the user's earlier challenges to the same address so a resend shows one enter box, writes trail rows for the opened challenge and for the answer as a hash, and writes the Challenged. row with the provider and the challenge tag in json. Enter finds the challenge by user and json tag, counts wrong guesses in the trail, rechecks the holder, and on a correct guess inserts the Proven. row then hides the challenge, on a held address hides it, and on the last wrong guess allowed hides it. Get reads every visible row of the type for the user, groups by f0, lets the highest stage win through credentialEventRanks with the newest face, and projects the live challenges for the enter boxes. Holder finds the Proven. row by type and f0. Remove hides every row about the address, whatever its stage. Grid tests cover the otp rules, the lifecycle sift, peers, claims, ownership, the race, and remove mid-challenge.

**Hidden today:** yes: the resend at Send, the closes at Enter through _otpHideChallenge, and Remove, plus close account, which hides Proven. only and leaves this type's mentions and challenges standing. Never hidden: every Mentioned. row, and a challenge abandoned past its twenty minutes. After: the mention is a ledger row only, Send deletes the earlier live challenge and inserts the new one so row_tick stays the challenge's clock, a correct guess deletes the challenge and inserts the proof, or edits the proof's json when the user re-proves an address she holds, a proof and a challenge for one address may stand at once, Remove deletes both, Get loses its rank map and grouping since the rows are the addresses, and a unique index on type and f0 among Proven. rows holds one holder per address.
