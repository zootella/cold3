# ledgerathon

The plan for the sprint that has every mutation of a live table write a ledger row beside it, from the same function that mutates, so nothing that happens here goes unrecorded: every credential flow, sign-up and close account, and beyond our own tables the dealings with third parties no record covers. It is the first of three sprints in a fixed order, planned in data.md: the ledgerathon, then hideless, which retires the hide column and converts every table to editing cells and deleting rows, then the smaller dog, which removes the Datadog apparatus. The order runs backward from the reason. Datadog can only leave once every change in the system has its record in ledger_table, and those records are only proven complete once the tables have stopped keeping history of their own, because a fact a mutating table loses is lost only to that table and never to the ledger. So this sprint runs first and soaks, for at least a week of real use, before hideless deletes anything.

The rule it installs is permanent. From the ledgerathon on, a new mutation arrives with its ledger row, in the same turn that writes it, and a review that finds a mutation without one has found a bug. It is a sprint of many sessions, and a new session takes it, reading this document to start. The first pass, the door pin and the oauth move, and the long pass, the inventory below, both landed September 8, 2026. The soak began September 9, 2026, when that pass reached production. What remains, in order: the push and deploy that give every row a door tag, the contraction that drops both scaffolding defaults and makes the door tag a rule the database holds, each dealing with a third party growing an open row and a close row around the call, the upload lambda writing its own rows, and the week of soak running underneath all of it.

## The three kinds of record

The ledger documents three kinds of thing, and documents each completely: everything we know at the moment, not less and not more. This is its charter, and it is what keeps the table useful the day staff in an audit are asking how this user did this, how this happened to this user, how it was possible at all, what happened. The inventory below is sorted by the three kinds without saying so.

- **Changes of state inside the application.** The create, update, and delete rows this document is mostly about: Alice changes her password, removes an email, adds a phone. Kept so a later version of the site can act on the history, reminding a user whose password is a year old, or showing staff what an account went through.
- **Complete records of every interaction with a third party.** We told Twilio this and they answered this, with the tick on each row, so a query can show that a send always took five seconds until August 7 and fifteen since. The round robin system reads these rows to alert staff to a provider misbehaving, and a robin running inside the site could balance away from a misbehaving provider by itself while staff sleep.
- **Records around addresses that could be contested between users.** Phone numbers, email addresses, wallet addresses, and oauth accounts: two users each believing they are alice.k@gmail.com, or someone scanning by misusing one of the credential flows. These rows are the radar that shows where the system is being pushed, kept running always so a vulnerability is understood from its record long after.

## What the ledger holds today

Verified against the hosted database and the code on September 7, 2026. ledger_table holds 2,910 rows, and 2,901 of them are hits, one per browser per hour. The rest are the three production call sites: the otp send in level3, whose row carries the whole task the lambda returned, and the two sites in the oauth handler, the proof or refusal at the callback and the cancel. Two rows still carry MessageSent., the action the send wrote before the vocabulary settled, and they stay as they are: the ledger is a notebook, an old row keeps the shape the code of its day gave it, and wrapper_hash points at that code. Nothing in production reads the table.

The shape is general on purpose, and this sprint asks nothing new of it. The margins, then wrapper_hash for the build that wrote the row; ip_text, origin_text, and client_json's geography and browser, filled from the door on every row; browser_hash and user_tag_text for who was here; action_text, event_text, and provider_text for what happened, in tags rather than codes; hash_text for a row's own hash when it has one, the browser's on a Browser. row or the visit's on a Hit., and blank otherwise; and json for everything else, the address or the name in its three forms included. Six indexes, by browser, user, action, hash, event, and provider, newest first. _ledgerRow in level3 is the one place a row is assembled, and it reads the door through getDoor, which tosses when there is none, because a ledger row with no request behind it is a bug in the caller.

## The rules

- **Every mutation of a live table writes its ledger row, and the function that mutates is the function that records.** Not the endpoint above it, so a new caller cannot forget, and a grid test that walks the function proves the row.
- **A ledger row says who acted, on what, from where, and when.** user_tag_text is the user who was authenticated to make the request. browser_hash, ip_text, origin_text, and client_json come from the door. row_tick is the moment. wrapper_hash is the build. json holds what happened, whole.
- **A row is complete, and duplicates nothing.** Complete: a row about a change of state carries every fact the function was given, an address or a name in all three of its forms under a key named for what it is, the guess or the code that was typed, the tag of the challenge; a row about a dealing with a provider carries the whole object we handed them and the whole object they handed back, however large. Not duplicated: a cell with no natural value stays blank. hash_text in particular holds a hash only when the row has one of its own, the browser's hash on a Browser. row or the visit's on a Hit.; an address is not a hash, so it rides json and hash_text stays blank, and nothing is hashed to fill a column.
- **A ledger row records what the function was asked to do, from the values it was given.** Never what the table held before the change or after it. The table change and the ledger write read the same local variables, and neither reads the other's result, so the two calls stay independent and the row can be written from the parameters alone. History is the rows read in order: the sessions a sign-out ended are the sign-ins above it, and the name a change replaced is the earlier Name. Proven. row.
- **A record table is never mutated, and a record gets no ledger row.** ledger_table, delay_table, and trail_table are appended to, and a wrong record is corrected by a later record.
- **A dealing with a third party is its own row, separate from the row about the user's data.** The otp send writes one row about Twilio, what we asked, what they answered, how long it took, and a second row that Alice's address is challenged; wallet prove step 2 writes one row about Alchemy and a second that the address is proven. A robin query by provider finds the first kind without wading through the second, and a staff query by user finds the second without the provider's payload in the way.
- **An old row is never migrated to the current shape.** The ledger is a notebook: a row keeps the shape the code of its day gave it, wrapper_hash names that code, and a reader who meets an old shape looks the build up rather than expecting the table to speak one language.
- **The ledger is the history.** A live table's own history, the hidden rows credential_table keeps today, is a duplicate with less in it, and hideless removes it once this sprint has made the ledger complete.

## The convention

Every mutating function in level3 has the same three parts, top to bottom: the checks on its parameters, the table change, and the ledger write, on adjacent lines, both reading the same locals. The ledger write comes after the table change succeeds. The endpoint passes nothing new, once the door carries the browser hash the way it carries the ip, origin, geography, and agent that _ledgerRow reads today. doorWorker and doorWorkerLite compute the hash from the cookie and hand it down as a parameter, and nothing pins it on the door, so a mutation deep in level3, credentialNameSet with its one userTag parameter, has no browser hash in hand. The sprint pins it as door.browserHash at the two doors that have one, _ledgerRow reads it from there by default, and the grid door gains one for the tests. The alternative, threading a browserHash parameter through every mutating signature, is a decision below. credentialOtpSend, which takes a browserHash parameter today only for its ledger row, drops it, so every function reads the hash the same way. The two oauth sites that write ledger rows from site code today move down: the proof row into credentialOauthSet, which already receives the provider's proof, and the refusal row beside it. The Cancelled. row stays in the handler, because a cancel at the provider mutates nothing and no level3 function runs; when hideless has a cancel delete the challenge row through a level3 call, the row moves down with it. Decided September 7, 2026.

ledgerAdd tosses without a door. Every mutation in production runs below one of the three doors, and every grid test runs below the grid door, so this costs nothing new. A one-off script that mutates rows would run its work inside doorAsyncLocalStorageRun with a small script door, which is a new and tiny thing to write the first time a script needs it.

A small first pass, then the long one. The long pass, done September 8, 2026, is the inventory below, type by type, each function with its ledger write beside its table change and its grid test asserting the rows; the two checks the endpoint did inline, the password compare at sign-in and the totp code check, became credentialPasswordVerify and credentialTotpVerify in level3, so their rows are written beside them and a grid test walks each. The upload lambda's rows are their own turn, still to come, since they touch net23's door, build, and deploy, and they want those steps finished first, because the rows the lambda writes should gather with the worker's under one door tag. And the sprint closes with an essay above ledger_table in level3, the table's charter written where the code is: the three kinds of record, the rule that a row is complete and duplicates nothing, what each column holds and when it stays blank, and the words in use, so the next reader meets the whole of it in one place.

## The vocabulary

action_text is the subject, which for credential_table is the credential type, Browser., Name., Password., Totp., Ethereum., Oauth., Email., or Phone., the same word the credential row carries in type_text, so a ledger query by action and a credential query by type speak the same names. event_text is the verb. Four are in use today: Challenged., Proven., Refused., and Cancelled. The rest arrive as the inventory below is coded, chosen at each site by two habits: the same word when it is the same thing, and the word the surrounding flow and its table already use, so a sign-in is Browser. Proven. because the user proved control of the browser, and a sign-out is Browser. Removed. because remove is what the function is called. The list is not an enumeration to complete or enforce: checkActionOrBlank checks the shape of a tag and not a list, a comment beside ledgerAdd lists the words in use, and the grid tests pin the exact word each flow writes.

## What json carries, and never carries

The facts that make the row useful later, that no column holds, and that the function was given: the tag of a challenge, the address forms, the connector a wallet came in over, the cycles of a password, the identifier and handle of an oauth link, the outcome of a refusal. Never a secret: no password hash, no totp secret. A wallet nonce rides the Challenged. row as it rides the credential row, since the page holds it in the clear anyway, and the Proven. row names the nonce that proved it. The one exception already decided stays decided, the otp send row holds the lambda's whole task with the message text, per data-cleanup.md's closed item, because the row is the complete record of what we did with the provider.

## The door tag, and the row's own tag

Two columns, and the difference between them is the point. door_tag is mandatory and says which single request wrote this row. tag_text is optional and says which single tagged thing the row is about, the way hash_text says which single hashed thing. The first gathers a request; the second gathers a subject.

door_tag came out of a question worth recording: is there any path into our code that reaches the database without a door? A check of all fifteen server entry points on September 9, 2026 said yes, there is not. Eleven api routes wear doorWorker, the oauth membrane wears doorWorkerLite, both lambda handlers wear doorLambda, and the three entry points with no door, the dev-restart endpoint, the nitro plugin, and the og-image middleware, touch no table. Every file in the repository that calls a database helper is one of those doored routes, icarus itself, or grid.js under the test door. So the tag is always in hand, which is what lets the database require it rather than the code merely providing it.

Underneath is AsyncLocalStorage, and it is what makes the column possible. The door rides in it, getDoor() reaches it from anywhere below through every await, and the runtime keeps each request's door separate even when several requests share one isolate. Nothing threads a parameter, so no function can forget to pass one. Threading a tag through every signature between an endpoint and credentialNameSet would have been a rule twenty functions had to remember, and a rule like that is one the database can never enforce.

The value for rows written before doors carried tags is twenty-one zeros, tag-shaped so every guard accepts it, and unmistakable on sight. It does two jobs: ADD COLUMN fills every existing row with it, so no backfill statement is needed, and it covers the window between the push and the deploy, when the worker still running inserts rows that never mention the cell.

So the choreography is the shape migration.md prescribes. The expansion adds door_tag with that default and creates ledger9. Then the deploy, where every door mints a tag and _ledgerRow puts it on every row. Then one contraction drops both scaffolding defaults, door_tag's and tag_text's, and from that moment an insert without a door tag fails, which is the database holding the rule instead of the code alone. The worker seals its tag into the Network23. envelope beside the browser hash, and the lambda door takes it over the one it minted, so the rows both providers write about one request gather together.

tag_text keeps the meaning hash_text has always had, one slot for the row's own singular tag. Nothing writes it yet. The otp rows are the obvious first use, since a challenge tag rides their json today as context, and the provider pairs below are the second: when one request talks to a provider twice, door_tag can no longer tell the two conversations apart, and a call tag in tag_text can.

## Every dealing with a provider, opened and closed

A dealing with a third party gets two rows, one before the call and one after: we are about to ask, and they answered with this. A provider that never answers leaves the first row with no second, and counting those unanswered halves is how we learn how often that happens. Today we would learn nothing, because we write the one row after the call returns, and a call that never returns writes nothing at all.

Nothing in our stack sets a timeout. fetchLambda and fetchProvider call $fetch without one, and the lambda's own send has none either, so a hung provider waits until Cloudflare kills the worker or Amazon kills the lambda. The message lambda gives up at ninety seconds; when it does, its function url answers with an error, $fetch throws, and today that throw travels past the rest of credentialOtpSend to the top gate, so we never record the challenge, even though the message may well have gone out. This step sets our own timeouts, so a quiet provider comes back as an ordinary error that closes the pair, and wraps the call at the bottom gate the way style.md says to, so the failure becomes a value the flow can act on. An orphaned open row then says something sharper than a slow provider: it says we died.

We already record the provider error itself, and that doesn't change. The lambda catches what the provider throws, keeps it on the task with the duration, and hands the task back, and the worker's row carries the whole of it. What the pair adds is the silence.

## The two writes

PostgREST has no transactions, so a table change and its ledger row are two round trips, one after the other. The order is the table change first and the ledger write second, so a ledger row never says something happened that didn't. Nothing special handles a failure. A failed call throws, the door answers the request with a 500, and the error lands in the provider dashboard. If the table change failed, nothing changed and no row was written. If the ledger write failed, the change stood and its row is missing, which is the gap hideless makes visible once rows are deleted rather than hidden. Server code can't be written to hold a predictable state through an unreliable database, so it doesn't try: no retry, no compensating write, no try/catch around either call. The two calls run in sequence rather than at once, because the comment at the bottom of report.js records that firing two Supabase calls at once from one request caused delays and 409 errors. If a missing row ever matters in practice, a Postgres function called through supabase.rpc runs inside one transaction and is the one path in the stack that could make the pair atomic, recorded here so the day it is needed nobody rediscovers it.

## The cost

An awaited ledger write is on the order of a hundred milliseconds on every path that mutates. Sign-in is the hottest of them and gains one write, on a path that already makes eleven round trips, and sign-ins are rare here: the browser tag cookie lives 395 days from the last visit, where other sites sign a user out after thirty days or an ip change. Accept it plainly: the paths are rare and human-paced, a person just typed a code or signed a message, and the alternative, a fire-and-forget successor to keepPromise, is exactly the parking lot the smaller dog is removing. Sign-up calls four functions and gets four rows in four calls, one from each, which is the price of the rule that the function that mutates is the function that records; sign-up is rare. ledgerAddMany stays for the day one function has several rows to write. A path that deals with a provider pays twice more once the pairs land, one write before the call and one after, and that is the price of learning which calls never came back.

## Testing

Every grid test that walks a flow asserts the ledger rows beside the credential rows: how many, which action and event, which hash, and the facts in json. Nothing in production reads ledger_table, and the tests need no reader of their own: the ledger tests already read rows with queryGet on ledger_table, filtered by action, user, or hash, and the flow tests read the same way. A ledgerGet family waits for the first staff page or robin query that wants one. A rule a test proves in isolation is worth little, so the assertions ride the flow tests, not a separate suite.

## Decisions the sprint must make

Each with a recommendation; the ones marked decided were taken September 7, 2026, and the rest are open.

- **Whether we ever leave a ledger write running.** No. Decided September 9, 2026: server code awaits every call to the database and to a third party, and the reasoning and its cost live in database-stack.md, since the rule reaches past this sprint. An audit that day found every database call in the repository already awaited, and the promise parking lot carrying nothing but Datadog.
- **Where a row gets its door tag, and whether the column is mandatory.** Mandatory, in a CHAR(21) the database requires, rather than an optional text cell the code merely fills. Decided and built September 9, 2026 on the strength of the entry-point check above: _doorWorkerHeaders mints for both worker doors, doorLambdaOpen mints its own, the sealed envelope carries the worker's across the hop, _ledgerRow reads door.tag and no caller may override it, and rows from before hold twenty-one zeros.
- **What tag_text holds.** The row's own singular tag, exactly as hash_text holds its own singular hash, and blank whenever the row is about no such thing. The question that made this a decision, which tag wins when a row could name two, went away when door_tag took the request: the request is never tag_text's business, so tag_text is free for the subject.
- **The verbs for a provider pair.** Asked. to open and Answered. to close, one pair for every third party, so a single query shape works across all of them. The Sent. and Asked. rows already written keep their words, as the notebook rule says. Recommended, not yet taken.
- **Where a mutation gets its browser hash.** Pinned on the door as door.browserHash by the two doors that compute one, and read by _ledgerRow by default, so no level3 signature changes, rather than threaded through every mutating function, which is the shape smaller-dog.md sketches for turnstile alone. credentialOtpSend drops the browserHash parameter it carries today only for its ledger row. Decided September 7, 2026.
- **The order of the two writes and the failure.** Table change first, ledger write second, in sequence, a failed call tosses to the top gate, and nothing else. Decided September 7, 2026, with the rpc escape hatch recorded.
- **The verb list.** Not an enumeration to complete or enforce. The same word when it is the same thing, and the word the surrounding flow and its table already use, chosen at each site as the inventory is coded, with a comment beside ledgerAdd listing the words in use. Decided September 7, 2026.
- **Whether refusals get rows.** Decided September 7, 2026, by two tests, either of which says yes: the refusal sits in a function whose other paths pair a table change with a ledger row, so leaving it out would be the one conspicuous gap in a painted fence; or the refusal is about, near, or could help tell the complete picture of an attack or malice. The exceptions are the paths where nobody else is involved and nothing is contested: a wrong first code during totp enrollment, a name that is taken or invalid, since names are public, the cycles lookup before sign-in, and a guess against a challenge that isn't live, the stale tab, which is counted as a start with no end rather than by rows of its own.

- **Whether Name. rows carry a hash_text.** No. Decided September 7, 2026: the normalized name already rides json, and a hash of it would duplicate the data for no query anyone runs.
